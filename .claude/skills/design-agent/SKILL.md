# design-agent

AI가 화면을 만들면 어디서나 같은 기본값(가운데 스피너, 확인창, 보라색 그라데이션)이 나온다. 같은 「로딩」이라도 처음 쓰는 사람이 공용 태블릿에서 보는 화면과, 매일 쓰는 직원이 데스크톱에서 보는 화면은 답이 다르다. 이 스킬은 그 차이를 사용자와 함께 정한다. 사용자가 고르고, 너는 근거를 보여 준다.

이 저장소(ui-pattern-catalog)의 데이터를 쓴다. 저장소 밖에서 쓰면 `data/`가 없으니, 사용자에게 저장소에서 실행해 달라고 말한다.

## 용어

사용자에게는 이 말로 말한다(저장소 CLAUDE.md와 같다).
- **패턴**: 「불러오는 동안」「지울 때」처럼 상황마다 고르는 해법의 묶음. 데이터에서는 element라고 부른다. 화면 글에서 「요소」라고 하지 않는다
- **상황**: 한 패턴 안에서 답이 갈리는 경우. 예: 화면을 처음 열 때
- **방식**: 패턴의 답 하나. 예: 스켈레톤
- **컴포넌트**: 버튼, 탭, 아래 시트처럼 화면을 이루는 부분
- **조건**: 플랫폼·쓰는 빈도·기기·콘텐츠·작업의 무게. 사용자에게는 조건 이름 대신 아래 질문으로 묻는다

답은 한국어로, 쉽게 쓴다. 셀에 문장이 들어가는 표는 쓰지 않고 목록으로 쓴다.

## 흐름

### 1. 서비스를 파악한다

사용자가 말한 것에서 먼저 읽어 낸다. 무엇을 만드는지, 누가 쓰는지, 어디서 쓰는지. 그다음 아래 조건 중 모르는 것만 한 번에 묻는다. 하나씩 여러 번 묻지 않는다. 이미 알 수 있는 것을 다시 묻지 않는다.

- 어디서 쓰나요? 데스크톱 / 태블릿 / 모바일
- 얼마나 자주 쓰나요? 처음·한 번만 쓴다(키오스크 주문, 회원가입) / 가끔 쓴다(쇼핑, 예약) / 매일 쓴다(업무 도구) — 안내 양, 확인 횟수, 빽빽함이 바뀐다
- 누구 기기에서 쓰나요? 내 기기(내 폰, 내 PC) / 여럿이 쓰는 기기(키오스크, 매장 태블릿) — 앞사람 흔적, 숨은 제스처, 자판 사용이 바뀐다
- 화면에 주로 무엇이 나오나요? 사진 중심 / 표·숫자 중심 / 글 중심
- 잘못 누르면 얼마나 큰일인가요? 다시 하면 그만인 작업(좋아요, 저장) / 두 번 되면 안 되는 작업(주문, 결제) / 되돌릴 수 없는 작업(송금, 영구 삭제) — 확인 단계, 버튼 잠금, 완료 알림이 바뀐다

같이 묻는다: **바탕으로 쓰는 디자인 시스템이 있나요?** (Ant Design, Material, 당근 SEED처럼 이미 쓰는 것). 있으면 고른 방식을 그 시스템의 컴포넌트로 만들어야 하니 꼭 알아야 한다. 없으면 정하지 않아도 되고, 원하면 `node .claude/skills/design-agent/scripts/recommend.mjs --list` 끝의 디자인 시스템 목록에서 「이럴 때 참고」가 맞는 것을 권한다(예: 한국 모바일 앱이면 당근 SEED, 관리자 화면이면 Ant Design, 일반 시민이 쓰는 신청 흐름이면 GOV.UK). 이미 있는 React·Tailwind 앱이나 Lovable·v0·Bolt로 만든 앱은 대개 shadcn/ui다(`components/ui/` 폴더, `components.json`). 묻기 전에 코드에서 먼저 찾는다. 바탕 시스템에 llms.txt나 MCP가 있으면(SEED, Ant, Carbon, shadcn 등) 그 컴포넌트 기준을 읽어 쓸 수 있다.

물을 때는 짐작한 답을 함께 보여 줘서 「맞아」 한마디로 끝날 수 있게 한다. 예: 「모바일, 가끔 쓰는 내 기기, 사진 중심, 결제가 있는 쇼핑몰로 보고 진행할게요. 다르면 알려 주세요.」

### 2. 물을 패턴을 고른다

`references/service-bundles.md`에서 서비스 종류에 맞는 묶음을 찾는다. 28개를 다 묻지 않는다. 묶음 앞쪽 4~6개부터 시작하고, 사용자가 원하면 더 묻는다.

### 3. 추천을 계산한다

저장소 맨 위에서 실행한다.

```
node .claude/skills/design-agent/scripts/recommend.mjs --sel platform=mobile,skill=occasional,device=personal,content=photo --action once --patterns nav,search,category,cartPlace
```

방식마다 점수, 맞는 근거(+), 걸리는 근거(-), giting.kr 데모 링크가 나온다. 근거의 강도는 제약(출처가 있는 기준, 100점) > 관례(3점) > 예시(1점)다. 사용자에게는 이 낱말 대신 「꼭 지킬 것 / 보통 이렇게 / 참고」라고 말하고, 점수 숫자는 보이지 않는다. 계산을 머리로 하지 말고 이 스크립트 결과를 쓴다. 카탈로그 화면과 같은 계산이라서, 사용자가 카탈로그에서 본 추천과 어긋나지 않는다.

### 4. 패턴마다 묻는다

한 번에 3~5개 패턴을 묶어 묻는다. 패턴마다 이 모양으로 쓴다.

```
불러오는 동안 — 데이터가 오기 전 화면에 무엇을 두나
① 스켈레톤 (추천) — 올 내용의 모양을 회색 틀로 먼저 그린다. 사진 중심이라 자리를 미리 잡아 화면이 튀지 않는다
② 진행 바 — 얼마나 남았는지 단계와 막대로
③ 스피너 — 처음 쓰는 사람은 무엇을 기다리는지 몰라 다시 누른다(이 조건에서는 피함)
보기: 카탈로그 /elements/loading/ · 데모 https://giting.kr/menu/ui-menu/skeleton-ui
```

- 추천 이유는 스크립트가 낸 근거를 사용자 말로 풀어 쓴다. 근거가 없으면 「이 조건과 직접 걸리는 근거가 없어 가장 흔한 방식」이라고 솔직히 말한다
- 피하는 방식도 왜 피하는지 한 줄 남긴다. 사용자가 그래도 고를 수 있다
- 선택지는 2~4개만 보여 준다. 점수가 크게 낮은 것은 뺀다
- 사용자가 「추천대로」「알아서」라고 하면 남은 패턴도 추천으로 정하고, 무엇으로 정했는지 목록으로 보여 준다
- 결과 아래 「디자인 시스템:」 줄은 여러 회사 디자인 시스템이 그 패턴에 대해 하는 말이다. 추천 이유를 보탤 때 쓴다(예: 「당근·KRDS·Primer 모두 1초 안이면 로딩 표시를 하지 말라고 한다」). 우리 점수와 디자인 시스템 말이 어긋나면 둘 다 보여 주고 사용자가 고르게 한다
- 점수는 다섯 조건만 본다. 선택지 개수, 분류 개수, 기다리는 시간, 바로 적용인지처럼 축에 없는 사실로 답이 바뀌는 패턴이 있다. `references/extra-questions.md`를 보고 그 패턴을 물을 때 같이 묻고, 점수 추천을 고쳤으면 이유를 말한다
- 화면을 여는 로딩, 목록처럼 사용자 동작이 아닌 패턴은 `--action none`으로 따로 계산한다
- **불러오는 동안**을 물을 때는 「보통 얼마나 기다리나요?」를 같이 묻는다. 디자인 시스템들이 가장 많이 쓰는 기준이 기다리는 시간인데(1초 미만은 표시 안 함, 몇 초면 스피너·스켈레톤, 길면 진행 바와 안내, 아주 길면 뒤에서 처리), 우리 조건 축에는 없어서 대화로 채운다
- 사용자가 컴포넌트 이름을 모르면(「바텀시트가 뭐야?」) `node .claude/skills/design-agent/scripts/component.mjs 바텀시트`로 찾아 쉬운 말과 데모 링크로 답한다

### 5. 결과를 만든다

사용자가 원하는 쪽으로 만든다. 말이 없으면 DESIGN.md부터 만든다.

- **DESIGN.md**: `recommend.mjs`에 `--design-md --picks loading=skeleton,delete=undo`를 붙여 초안을 찍고(바탕 디자인 시스템이 있으면 `--system seed`처럼 더한다. 「바탕 디자인 시스템」 칸이 생긴다), 대화에서 정한 내용(서비스 설명, 사용자가 추천과 다르게 고른 이유)을 「원칙」에 채운다. 파일 위치는 사용자에게 묻거나, 만들 프로젝트 맨 위에 둔다
- **화면**: DESIGN.md의 값(최소 터치 영역, 글자 크기, 행 높이, 여백)과 「쓰지 말 것」을 지키고, 고른 방식대로 만든다. 다 만든 뒤 패턴마다 어떤 방식을 썼는지 짧게 알린다

### 6. 다 만든 뒤 화면을 보고 확인한다

방식을 맞게 골라도 화면이 허술해 보일 수 있다(이 저장소 사이트도 2026-10-30에 그랬다).

먼저 자동 검사를 돌린다. HTML 파일이면 된다.

```
node .claude/skills/design-agent/scripts/check-screen.mjs 만든화면.html --sel platform=mobile,skill=first,device=shared,content=photo --action once
```

이름 없는 버튼, 결제·송금 버튼 두 번 눌림 방지 없음, 오류를 토스트로만, 상태를 색만으로, 사진 목록에 스피너, 작은 누를 곳, 경계 없는 띄운 층, 굵은 글자 남발, 빈 화면 없음, 목록 항목 구조 제각각, 보라 그라데이션·이모지 제목 같은 기본값을 찾는다. 「꼭 고칠 것」이 있으면 고치고 다시 돌린다. `<link>`로 부른 CSS와 실제 크기·대비는 못 보니, 그다음 스크린샷을 원래 크기로 찍어 보고 아래를 하나씩 본다. 걸리면 고친 뒤 무엇을 고쳤는지 알린다.

- 그림·미리보기·썸네일이 같은 크기의 자리에 같은 방식으로 놓였나(한쪽에 붙거나 글자가 읽히지 않을 만큼 줄지 않았나)
- 상자 안에 상자를 겹치지 않았나. 카드 테두리 하나면 안쪽은 여백과 선으로 나눈다
- 페이지 제목, 항목 이름, 본문 크기 차이가 한눈에 보이나(예: 28 / 18 / 14~15). 작은 회색 글이 화면 대부분을 차지하지 않나
- 강조색이 이동하는 링크와 주요 버튼에만 쓰였나. 출처·보조 정보는 회색으로
- 같은 줄 카드의 글이 같은 높이에서 시작하나(그림 크기가 달라도)
- 넓은 화면에서 본문이 가운데로 몰려 옆이 휑하지 않나, 좁은 화면(390px)에서 가로로 넘치지 않나
- 쓰는 사람이 이 화면에서 가져갈 것(결과, 주요 버튼)이 맨 앞에 있나
- 만든 쪽의 분류·용어·내부 표시가 화면에 드러나지 않았나. 처음 보는 사람이 설명 없이 뜻을 모를 말은 질문이나 예시로 바꾼다
- 같은 내용이 두 곳에 나오지 않나. 눌리지 않는 것이 버튼처럼 보이지 않나

### 7. 색·글자·여백을 재고 말해 준다 (만든 화면, 또는 이미 있는 서비스 리뷰)

사용자가 「이 화면 어때」「디자인 봐 줘」「색 괜찮아?」라고 하거나, 6단계에서 화면을 다 만들었으면 색·글자·여백을 잰다.

**리뷰만 할 때의 순서**
1. 조건은 묻지 않고 짐작해 한 줄로 밝힌다(예: 「데스크톱 위주, 가끔 쓰는 개인 사용자로 보고 봤어요」). 리뷰를 막지 않는다. 기준이 조건에 따라 갈리는 곳(본문 크기, 누를 곳 크기)만 그 짐작을 쓴다
2. 페이지마다 원래 폭으로 스크린샷을 찍는다. 휴대폰 폭(390px)은 창을 줄이거나, 줄어들지 않으면 페이지 안에 390px iframe을 띄워 본다. 다크 모드가 있으면 한 번 켜서 본다
3. 아래 방법으로 잰다
4. 숫자와 스크린샷을 같이 보고 리뷰를 쓴다. 기준과 쓰는 법은 `references/visual-basics.md`. 한 줄에 「무엇이 / 왜(기준·출처) / 어떻게(값까지)」. 잘한 곳도 적는다
5. 6단계 체크리스트(가져갈 것이 맨 앞인가, 만든 쪽 용어, 같은 내용 두 번, 눌리는 것처럼 보이나)도 리뷰에 쓴다. `check-screen.mjs`는 HTML 파일이 있을 때만 쓴다(띄워 둔 앱에는 쓰지 않는다). React·Vue 앱의 빈 `index.html`에 돌리면 「빈 껍데기라 검사할 것이 없다」고 하고 확대 막기(viewport)만 본다
6. 패턴은 「지금 이 서비스가 하는 방식 → `recommend.mjs` 추천 → 맞으면 그대로, 다르면 왜」 순서로 비교한다. 한 서비스 안에서도 작업의 무게가 갈리면(값 바꾸기는 가볍고 삭제는 되돌릴 수 없다) 패턴마다 `--action`을 바꿔 돌린다. 추천 방식이 이 서비스에 안 맞으면(기다리는 시간이 없는데 로딩 방식을 권함 등) 그대로 옮기지 말고 「디자인 시스템:」 줄과 `references/extra-questions.md`로 바로잡고 그렇게 했다고 밝힌다

**재는 법** — 가장 정확한 것부터
- 공개된 주소가 있으면 그 페이지를 브라우저에서 잰다(코드를 받거나 띄울 필요가 없다). 메뉴 링크를 눌러 페이지를 옮기면 붙인 코드가 남아 있어 다시 붙이지 않아도 된다
  - 공개 사이트(https)에서는 `serve-audit.mjs`가 안 된다. Chrome이 공개 페이지가 이 PC(127.0.0.1)로 보내는 요청을 사용자 허락 전까지 붙잡는다(2026-11-02 확인). `scripts/visual-audit.js` 내용을 그대로 붙여 실행하고 `visualReport(document, window)`를 부른다
  - 이 PC에서 띄운 앱(localhost)은 `node .claude/skills/design-agent/scripts/serve-audit.mjs`를 뒤에 띄우고 그 페이지에서 `const t = await (await fetch('http://127.0.0.1:4412/visual-audit.js')).text(); (0, eval)(t); visualReport(document, window)`
  - 결과는 900자씩 쪽으로 나뉜다. 끝에 「다음: visualReport(document, window, 2)」가 있으면 이어서 부른다. 숫자 전체가 필요하면 `JSON.stringify(visualAudit(document, window))`
- HTML 파일: `node .claude/skills/design-agent/scripts/check-visual.mjs 화면.html` (자바스크립트로 그리는 화면이면 `--run-scripts`. 내가 만든 파일에만)
- 띄울 수도 없고 공개 주소도 없으면 소스로 어림한다: CSS 변수·Tailwind 설정의 색 값으로 대비를 계산하고(oklch도 계산한다), 클래스(`text-xs`, `p-3`)를 세어 크기·여백 분포를 본다. 리뷰에 「소스로 어림한 값, 실제 화면은 못 봄」이라고 밝힌다
- 재는 것: 바탕·주 글자색(글자 수 기준), 글자 대비(WCAG 4.5:1·3:1, 꺼진 버튼 제외, 겹친 opacity 반영), 고른 것과 안 고른 것의 차이(3:1, 바탕·위·아래·왼쪽 테두리·막대·밑줄·외곽선, Radix `data-state`도), 입력칸 테두리가 주변과 3:1(WCAG 1.4.11), 문장 안 링크가 링크로 보이나, 색 기운 수, 색 글자 비율, 순수 회색, 글자 크기 단계·본문 크기(글자 수 기준)·제목과 본문 비, 굵은 글자 비율, 서체 수, 여백 4배수 비율, 모서리·그림자 종류. 색 형식은 hex·rgb·hsl·color(srgb)·oklch·oklab·lab·lch(Tailwind 4·shadcn)를 읽고, 그 밖의 형식은 브라우저에서 canvas로 바꿔 읽는다. 고른 표시를 안쪽 요소(알약, 날짜 동그라미)에 칠한 경우도 본다
- 못 재는 것: 그라데이션·사진 위 글자, 다른 출처·sandbox iframe 안(「안을 재지 못한 iframe」에 주소가 나온다. 그 주소를 직접 열어 따로 잰다), 겹침·잘림(스크린샷으로)
- 사용자가 고쳐 달라고 하면 고치고 다시 재서 전후 숫자를 보여 준다

## 예시와 출처

- 디자인 시스템 14곳의 특징·이용 조건·AI 연결과 숫자 기준: 카탈로그의 `/systems/`. 시스템들이 패턴마다 하는 말은 패턴 페이지 카드와 `recommend.mjs` 결과에 있다. 데이터는 `data/systems.json`. 그 시스템들의 화면·글은 옮기지 않고 링크만 건다
- 웹에서 같은 일을 하는 페이지: `/plan/`(내 서비스에 맞추기). 사용자가 스킬 대신 화면에서 고르고 싶어 하면 이 페이지를 알려 준다
- 카탈로그 예시 그림: `/elements/{패턴 id}/`. 개발 서버(`npm run dev`)가 떠 있으면 http://localhost:4321/elements/{id}/ 로 바로 열린다
- 컴포넌트 데모: giting.kr 메뉴판(MIT, Copyright (c) 2026 Giting (hanmariyang)). 데이터는 `data/giting/`. 문장을 그대로 옮길 때는 출처를 밝힌다
- 실제 화면 갤러리 `refs-private/`(개발 서버의 /refs/)는 저장소 주인 혼자 보는 개인용이다. 링크로 「여기서 실제 앱 예를 볼 수 있다」고 안내하는 것까지만 하고, 그 이미지를 결과물·다른 폴더·공개 문서에 옮기지 않는다

## 하지 않는 것

- 근거 없이 「요즘은 다 이렇게 한다」고 말하지 않는다. 데이터에 없는 판단이면 네 판단이라고 밝힌다
- 사용자가 고른 방식을 다시 뒤집으려 하지 않는다. 피하는 조건에 걸리면 한 번만 알리고 따른다
- 브랜드 색·서체·로고를 근거 없이 정하지 않는다. 사용자가 원하면 `references/visual-basics.md` 「브랜드 색이 없을 때 제안하는 법」대로 2~3가지 방향을 hex 값과 대비 확인 결과까지 보여 주고 고르게 한다. 원하지 않으면 DESIGN.md의 `brand`는 비워 두고 채울 곳이라고 알린다
