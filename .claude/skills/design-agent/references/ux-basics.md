# 쓰는 흐름 기준 (UX)

`visual-basics.md`가 화면의 값(색·글자·여백)을 다룬다면, 이 문서는 쓰는 흐름을 다룬다: 무엇을 누르면 무슨 일이 나고, 실수하면 어떻게 되고, 지금 무엇을 해야 하는지 보이는가. 화면을 만들 때 지키고, 리뷰할 때 7단계 「눌러 본다」에서 이 순서대로 본다.

규칙의 모양은 공개 기준과 디자인 시스템이 쓰는 방식을 따랐다(조사: `research/ux-rules.md`, 2026-11-11). 계기는 직접 만든 내부 도구 화면 비교에서 확인 창이 위험 버튼에 첫 초점을 두고 열리는 것을 값 검사도 사람 리뷰도 못 본 일이다.

## 읽는 법

**규칙마다 칸이 다섯이다.**

- 규칙: 한 문장. 리뷰에서는 이름(`사고-1`)으로 부른다
- 예외: 이 규칙을 쓰지 않는 경우. 예외가 없으면 줄을 뺀다
- 눈으로: 리뷰하는 쪽이 화면에서 해 보는 것
- 검사: 스크립트가 잡는 것. 없으면 「없음」이고, 눈으로 본 것만 말한다
- 근거: 같은 말을 하는 공개 기준. 출처가 없는 우리 규칙은 그렇다고 적는다

**수준은 규칙에 붙어 있다.** 스킬의 「꼭 / 권장 / 확인」을 KRDS 서비스 패턴의 정의에 맞춰 쓴다.

- 꼭: 못 지키면 과업이 실패하거나, 되돌릴 수 없는 일이 사용자 뜻과 다르게 일어난다. 사용자가 스스로 피할 방법이 없다
- 권장: 못 지키면 어려워지거나 느려지지만 끝낼 수는 있다
- 확인: 맞고 틀림이 서비스마다 갈린다. 지적하지 말고 정한 건지 묻는다

**심각도는 리뷰에서 매긴다.** 같은 「권장」이라도 그 화면에서 얼마나 아픈지는 다르다. 「먼저 고칠 셋」을 고를 때는 세 가지를 본다: 과업을 못 끝내나, 얼마나 자주·많이 겪나, 되돌릴 수 있나(NN/g 심각도 기준과 같은 갈래).

**서비스마다 갈리는 것은 「서비스 안에서 하나로」가 규칙이다.** 확인 창 버튼 순서, Esc로 닫히는지, 확인 창의 빨간 버튼은 회사마다 다르다. 한쪽을 정답으로 두지 않고, 한 서비스 안에서 섞여 있으면 짚는다.

**서비스가 정한 것이 먼저다.** 판단 순서는 SKILL.md 「서비스에서 정한 규칙」과 같다: 규격(WCAG, 되돌릴 수 없는 사고) > 서비스가 정한 것 > 이 문서의 권장.

## 사고 위험

되돌릴 수 없는 일이 사용자 뜻과 다르게 일어나는 것. 실패 이름은 「사고 위험」.

- **사고-1 (꼭) 위험한 확인 창은 안전한 쪽에 첫 초점을 둔다.**
  - 눈으로: 확인 창을 열고 바로 Tab이나 Enter를 누르면 어디가 눌리는지 본다. 창을 연 버튼으로 Enter를 쳐서 열면 그 다음 Enter가 곧 확정이 된다
  - 검사: `check-screen.mjs` 「위험 버튼에 첫 초점」(스크립트로 초점을 옮기는 화면은 오판할 수 있다)
  - 근거: WAI-ARIA APG 모달 대화상자(되돌릴 수 없으면 가장 덜 파괴적인 동작에), Carbon 모달 접근성, Primer ConfirmationDialog, NN/g 확인 창(기본값을 「예」로 두지 않는다)
- **사고-2 (꼭) 확인 창은 무엇이 사라지고 되돌릴 수 있는지 말한다.**
  - 「정말 하시겠어요?」만 있으면 안 된다. 대상의 이름과 결과를 쓴다. 양을 알 수 있으면 수로 쓴다(「결과 파일 12개」)
  - 눈으로: 확인 창 글만 읽고 무엇이 없어지는지 답할 수 있나
  - 검사: 「정말 ~하시겠어요?」 제목, 「확인·예」 버튼(`check-screen.mjs`)
  - 근거: KRDS 모달(기능·결과·위험을 반드시 설명), NN/g 확인 창, Primer·Shopify(되돌릴 수 없다는 사실을 작은 글씨에 묻지 않는다), Atlassian(되돌릴 수 있는지 밝힌다). 수로 쓰라는 것은 우리가 더했다
- **사고-3 (권장) 화면에서 가장 강조된 버튼이 되돌릴 수 없는 동작이 아니다.**
  - 첫 입구는 일반 버튼으로 두고, 빨강·채움 같은 강한 신호는 마지막 확인 단계에만 쓴다
  - 예외: 그 화면이 오직 그 일을 하려고 있는 화면(탈퇴 화면의 「탈퇴」)
  - 눈으로: 화면에서 채운 버튼·색 버튼이 무엇인지 보고, 그것이 지우기·종료·보내기인지 본다
  - 검사: 없음
  - 근거: GOV.UK 버튼(경고 버튼은 마지막 확인에만, 첫 동작은 일반 버튼), 주 버튼은 한 페이지에 하나. 「가장 강조된 버튼」으로 묶은 것은 우리 규칙이다
- **사고-4 (권장) 되돌리기 쉽거나 자주 하는 동작에는 확인 창 대신 되돌리기를 준다.**
  - 확인 창이 잦으면 읽지 않고 누르게 되어, 정말 위험한 확인도 같이 무뎌진다
  - 눈으로: 하루에 여러 번 하는 동작마다 확인 창이 뜨나
  - 검사: 없음. 방식 고르기는 `recommend.mjs --patterns delete --action light`
  - 근거: Primer ConfirmationDialog(위험이 낮고 되돌리기 쉬우면 쓰지 않는다), Apple 경고창(흔하고 되돌릴 수 있는 삭제에는 띄우지 않는다)

## 키보드와 초점

마우스 없이도 쓸 수 있고, 초점이 사라지거나 엉뚱한 데로 가지 않는 것. 실패 이름은 「읽기·누르기 어려움」.

- **키보드-1 (꼭) 모든 기능을 키보드로 쓸 수 있고, 초점이 갇히지 않는다.**
  - 눈으로: Tab만으로 주요 동작을 끝까지 해 본다. 들어간 곳에서 Tab·Shift+Tab·Esc로 빠져나올 수 있나
  - 검사: 「키보드로 못 누르는 곳」(`check-screen.mjs`, onclick·@click만 단 div·span·li·img. 스크립트에서 붙인 클릭은 못 본다), 이름 없는 버튼. 흐름 전체는 없음
  - 근거: WCAG 2.2 2.1.1, 2.1.2
- **키보드-2 (권장) 대화상자는 안에서 초점이 돌고, 닫으면 연 자리로 돌아간다.**
  - 연 버튼이 사라졌으면(지운 행) 흐름상 다음 자리(이웃 행)로 보낸다. 페이지 맨 위로 떨어지게 두지 않는다
  - 눈으로: 창을 열고 Tab을 여러 번 눌러 창 밖으로 나가지 않는지, 닫은 뒤 초점이 어디 있는지 본다
  - 검사: 없음
  - 근거: WAI-ARIA APG 모달 대화상자, Primer 초점 관리, Fluent Dialog, Carbon 대화상자 패턴
- **키보드-3 (권장) 꼭 필요한 정보가 마우스 올림 설명(title, 툴팁)에만 있지 않다.**
  - 키보드·터치로는 볼 수 없다. 꺼진 버튼의 이유, 위험 안내는 화면에 글로 둔다
  - 눈으로: `title`이 달린 꺼진 버튼, 아이콘에만 붙은 설명을 찾는다
  - 검사: 「꺼진 이유가 title에만 있음」(`check-screen.mjs`, 꺼진 버튼이나 감싼 span의 title. 툴팁 라이브러리는 못 본다)
  - 근거: WCAG 2.2 1.4.13, NN/g 툴팁 글(과업에 필요한 정보는 화면에), Primer 툴팁·디자이너 체크리스트, Carbon 비활성 상태(막혔으면 풀 방법을 인라인으로)
- **키보드-4 (확인) Esc로 닫히는지, 확인 창 버튼 순서가 서비스 안에서 하나로 맞다.**
  - 갈리는 기준이다. Primer·Carbon은 Esc로 닫히고 Fluent의 경고 창은 닫히지 않는다. 버튼 순서는 Carbon·Apple이 「취소 왼쪽, 확정 오른쪽」, GOV.UK는 주 동작이 먼저다
  - 눈으로: 확인 창 두세 개를 열어 순서와 Esc 동작이 같은지 본다
  - 검사: 없음

## 할 일이 보이나

화면을 열었을 때 지금 상태와 해야 할 일이 바로 보이는 것. 실패 이름은 「할 일이 안 보임」.

- **할 일-1 (권장) 첫 화면 높이 안에 지금 상태가 보인다.**
  - 진행 중인지, 막혔는지, 끝났는지. 상태를 보려고 끝까지 내려가야 하면 안 된다
  - 눈으로: 스크롤하지 않은 첫 화면만 보고 「지금 어떤 상태고 내가 뭘 하면 되나」에 답해 본다
  - 검사: 없음
  - 근거: NN/g 1번 휴리스틱(시스템 상태 보이기), KRDS 신청 패턴 [필수] 현재 진행 상태 제공, Built for Shopify 4.2.3(첫 화면에 잘 돌고 있는지)
- **할 일-2 (권장) 핵심 요약은 앞에 한 번만 둔다.**
  - 결과 수·합계처럼 화면 전체를 요약하는 것은 맨 아래가 아니라 위에. 같은 상태 글(「진행 중 아님」)을 여러 곳에 되풀이하지 않는다
  - 눈으로: 요약 숫자가 어디 있는지, 같은 글이 몇 번 나오는지 센다
  - 검사: 없음
  - 근거: Fluent·Microsoft 글쓰기(가장 중요한 것을 앞에), 토스 라이팅 원칙(화면 속 잡초 제거), Shopify(같은 내용을 한 페이지에 두 번 보이지 않는다)
- **할 일-3 (확인) 상태에 따라 강조가 바뀐다.**
  - 다 끝났으면 마무리 동작을, 막혔으면 막힌 이유를 앞에 둔다. 할 일이 없을 때 강조할 것도 없다
  - 눈으로: 상태를 바꿔 본다(`references/try-pages.md` 「상태 바꿔 보기」). 상태가 바뀌어도 같은 버튼이 늘 같은 강도로 있으면 짚는다
  - 검사: 없음
  - 근거: 직접 다룬 출처는 찾지 못했다. 우리 규칙이다. 가까운 것은 Built for Shopify 4.2.5(가장 그럴듯한 버튼을 강조), GOV.UK(주 버튼은 하나)

## 누른 뒤

누른 다음 무엇이 바뀌었는지 알고, 실패하면 그 자리에서 고칠 수 있는 것. 실패 이름은 「빠진 상태」.

- **누른 뒤-1 (권장) 결과를 작업한 자리에서 알린다.**
  - 무엇이 바뀌었는지, 다른 화면으로 옮겨졌으면 왜 거기 왔는지. 성공 알림은 보조기술도 읽게(`role="status"`, `aria-live`)
  - 예외: 결과가 화면에 그대로 보이는 가벼운 동작(체크 켜기)은 따로 알리지 않아도 된다
  - 눈으로: 눌러 보고 1초 안에 무엇이 달라졌는지 말할 수 있나. 다른 목록으로 넘어갔다면 방금 한 일이 어디 남았나
  - 검사: 없음
  - 근거: NN/g 1번 휴리스틱, Carbon 알림 패턴(작업한 영역에 바로), Primer 저장 패턴(페이지가 그대로면 인라인 메시지), GOV.UK 완료 페이지, WCAG 2.2 4.1.3
- **누른 뒤-2 (꼭) 실패하면 그 자리에 이유가 남고, 입력이 지워지지 않는다.**
  - 사라지는 토스트로만 알리지 않는다. 다시 할 방법을 같이 쓴다
  - 눈으로: 빈 칸·틀린 값으로 제출하고, 실패 뒤에도 입력이 남는지 본다
  - 검사: 오류를 토스트로만 알림(`check-screen.mjs`)
  - 근거: GOV.UK 오류 메시지(필드 옆, 입력값 보존), Carbon 모달(닫지 않고 인라인), Built for Shopify 4.2.4, NN/g 오류 메시지 글, WCAG 2.2 3.3.1·3.3.3

## 말

버튼과 안내 글이 하는 일을 정확히, 한 목소리로 말하는 것. 실패 이름은 「헷갈림」.

- **말-1 (권장) 버튼 이름은 하는 일을 말한다.**
  - 「확인」「예」「완료」 대신 「삭제」「종료」「보내기」. 확인 창 제목의 동사와 버튼 이름을 맞춘다. 닫기만 하는 쪽은 「취소」보다 「닫기」가 오해가 적을 때가 있다(「QA 취소」로 읽히는 경우)
  - 예외: 알리기만 하는 창의 「확인」
  - 눈으로: 버튼 글만 읽고 누른 뒤 무슨 일이 나는지 답할 수 있나
  - 검사: 버튼이 둘인데 「확인·예」인 대화상자(`check-screen.mjs`)
  - 근거: 조사한 모든 곳이 같은 말을 한다(Apple, Carbon, Shopify, Primer, Atlassian, Fluent, GOV.UK, KRDS, 토스). 「닫기」는 앱인토스 소비자 UX 가이드
- **말-2 (확인) 한 화면 안에서 말투가 섞이지 않는다.**
  - 「~해요」「~합니다」「~다」가 한 화면에 섞이면 여러 사람이 만든 화면처럼 읽힌다. 상황에 따라 바뀌어도 되는 것은 어조(오류는 더 짧고 직접)이고, 말투는 하나로 둔다
  - 예외: 사용자에게 하는 말(안내·상태·오류)과 사전식 설명(컴포넌트 정의, 목록의 짧은 설명)을 다른 말투로 정해 둔 서비스. 그 경우는 갈래마다 하나로 맞는지를 본다(이 카탈로그 사이트가 그렇다. 2026-11-11)
  - 눈으로: 안내 글·빈 화면·오류·확인 창 글의 끝맺음을 모아 본다
  - 검사: 「말투가 섞임」(`check-screen.mjs`, 끝맺음이 있는 문장의 해요체·합니다체·한다체가 각각 2번 넘게 나오면. 질문·버튼 글은 세지 않는다. `--rules`·`--house`에서는 「정한 건지 확인」으로 간다)
  - 근거: Shopify 콘텐츠(목소리는 같게, 어조는 상황에 맞게), 토스(해요체 필수), NN/g 일관성 글. 글투는 서비스가 정하는 것이라 「확인」이다

## 리뷰에 쓰는 법

- 걸린 규칙은 「무엇이 / 왜(규칙 이름과 근거) / 어떻게」 한 줄로, 실패 이름 아래에 둔다
- 「검사: 없음」인 규칙은 눌러 보고 확인한 것만 쓴다. 못 해 본 것(로그인 뒤, 지우기처럼 남에게 영향이 가는 동작)은 「확인 못 한 것」에 적고 위반이라고 하지 않는다
- 「먼저 고칠 셋」은 값 검사와 이 문서를 같이 놓고 고른다. 「꼭」이 걸렸으면 대개 그것이 먼저다
- 화면을 만드는 쪽이면: 「꼭」은 모두 지키고, 「권장」은 계획에 어떻게 할지 한 줄씩 적는다
