# 쓰는 흐름 기준 (UX)

<!-- data/ux.json에서 만든다. 고칠 때는 data/ux.json을 고치고 node tools/ux-doc.mjs를 돌린다 -->

`visual-basics.md`가 화면의 값(색·글자·여백)을 다룬다면, 이 문서는 쓰는 흐름을 다룬다: 무엇을 누르면 무슨 일이 나고, 실수하면 어떻게 되고, 지금 무엇을 해야 하는지 보이는가. 화면을 만들 때 지키고, 리뷰할 때 7단계 「눌러 본다」에서 이 순서대로 본다.

규칙의 모양은 공개 기준과 디자인 시스템이 쓰는 방식을 따랐다(조사: `research/ux-rules.md`, 2026-11-11). 계기는 직접 만든 내부 도구 화면 비교에서 확인 창이 위험 버튼에 첫 초점을 두고 열리는 것을 값 검사도 사람 리뷰도 못 본 일이다.

## 읽는 법

**규칙마다 칸이 다섯이다.**

- 규칙: 한 문장. 리뷰에서는 이름(`사고-1`)으로 부른다
- 예외: 이 규칙을 쓰지 않는 경우. 예외가 없으면 줄을 뺀다
- 눈으로: 리뷰하는 쪽이 화면에서 해 보는 것
- 검사: 스크립트가 잡는 것. 없으면 「없음」이고, 눈으로 본 것만 말한다
- 근거: 같은 말을 하는 공개 기준. 출처가 없는 우리 규칙은 그렇다고 적는다. 원문을 못 열고 요약·기사로만 본 출처는 「간접」을 붙인다

**수준은 규칙에 붙어 있다.** 스킬의 「꼭 / 권장 / 확인」을 KRDS 서비스 패턴의 정의에 맞춰 쓴다.

- 꼭: 못 지키면 과업이 실패하거나, 되돌릴 수 없는 일이 사용자 뜻과 다르게 일어난다. 사용자가 스스로 피할 방법이 없다
- 권장: 못 지키면 어려워지거나 느려지지만 끝낼 수는 있다
- 확인: 맞고 틀림이 서비스마다 갈린다. 지적하지 말고 정한 건지 묻는다

**심각도는 리뷰에서 매긴다.** 같은 「권장」이라도 그 화면에서 얼마나 아픈지는 다르다. 「먼저 고칠 셋」을 고를 때는 세 가지를 본다: 과업을 못 끝내나, 얼마나 자주·많이 겪나, 되돌릴 수 있나(NN/g 심각도 기준과 같은 갈래).

**서비스마다 갈리는 것은 「서비스 안에서 하나로」가 규칙이다.** 확인 창 버튼 순서, Esc로 닫히는지, 확인 창의 빨간 버튼은 회사마다 다르다. 한쪽을 정답으로 두지 않고, 한 서비스 안에서 섞여 있으면 짚는다.

**서비스가 정한 것이 먼저다.** 판단 순서는 SKILL.md 「서비스에서 정한 규칙」과 같다: 규격(WCAG, 되돌릴 수 없는 사고) > 서비스가 정한 것 > 이 문서의 권장.

## 사고 위험

되돌릴 수 없는 일이 사용자 뜻과 다르게 일어나는 것. 실패 이름은 「사고 위험」.

- **사고-1 (꼭) 위험한 확인 창은 안전한 쪽에 첫 초점을 둔다.**
  - 눈으로: 확인 창을 열고 바로 Tab이나 Enter를 누르면 어디가 눌리는지 본다. 창을 연 버튼으로 Enter를 쳐서 열면 그 다음 Enter가 곧 확정이 된다
  - 검사: `check-screen.mjs` 「위험 버튼에 첫 초점」(스크립트로 초점을 옮기는 화면은 오판할 수 있다)
  - 근거: WAI-ARIA APG 모달 대화상자(되돌릴 수 없으면 가장 덜 파괴적인 동작에), Carbon 모달 접근성, Primer ConfirmationDialog, NN/g 확인 창(기본값을 「예」로 두지 않는다)
- **사고-2 (꼭) 확인 창은 무엇이 사라지고 되돌릴 수 있는지 말한다.**
  - 「정말 하시겠어요?」만 있으면 안 된다. 대상의 이름과 결과를 쓴다. 양을 알 수 있으면 수로 쓴다(「결과 파일 12개」)
  - 눈으로: 확인 창 글만 읽고 무엇이 없어지는지 답할 수 있나
  - 검사: 「정말 ~하시겠어요?」 제목, 「확인·예」 버튼(`check-screen.mjs`)
  - 근거: KRDS 모달(기능·결과·위험을 반드시 설명), NN/g 확인 창, Primer·Shopify(되돌릴 수 없다는 사실을 작은 글씨에 묻지 않는다), Atlassian(되돌릴 수 있는지 밝힌다). 수로 쓰라는 것은 우리가 더했다
- **사고-3 (권장) 되돌릴 수 없는 동작을 화면에서 가장 눈에 띄는 버튼으로 두지 않는다.**
  - 첫 입구는 보통 버튼으로 두고, 빨간 버튼·채운 버튼 같은 강한 신호는 마지막 확인 단계에만 쓴다
  - 예외: 그 화면이 오직 그 일을 하려고 있는 화면(탈퇴 화면의 「탈퇴」)
  - 눈으로: 화면에서 채운 버튼·색 버튼이 무엇인지 보고, 그것이 지우기·종료·보내기인지 본다
  - 검사: 없음
  - 근거: 우리 규칙이다. 가까운 것은 GOV.UK 버튼(경고 버튼은 마지막 확인에만, 첫 동작은 일반 버튼. 주 버튼은 한 페이지에 하나)
- **사고-4 (권장) 되돌리기 쉽거나 자주 하는 동작에는 확인 창 대신 되돌리기를 준다.**
  - 확인 창이 잦으면 읽지 않고 누르게 되어, 정말 위험한 확인도 같이 무뎌진다
  - 눈으로: 하루에 여러 번 하는 동작마다 확인 창이 뜨나
  - 검사: 없음. 방식 고르기는 `recommend.mjs --patterns delete --action light`
  - 근거: Primer ConfirmationDialog(위험이 낮고 되돌리기 쉬우면 쓰지 않는다), Apple 경고창(흔하고 되돌릴 수 있는 삭제에는 띄우지 않는다)
- **사고-5 (꼭) 새로 고침·뒤로 가기·두 번 누르기로 같은 제출(결제·전송)이 다시 일어나지 않는다.**
  - 누르면 요청이 끝날 때까지만 버튼을 잠그고 진행을 보인다. 미리 꺼 두지는 않는다(입력-4). 처리한 뒤에는 결과 주소로 옮겨(Post/Redirect/Get, 한 페이지 앱은 기록을 replace) 새로 고침이 같은 요청을 다시 보내지 않게 하고, 서버도 같은 요청을 한 번만 처리한다
  - 눈으로: 완료 화면에서 새로 고침을 눌러 브라우저가 「양식 다시 제출」을 물으면 위반이다. 완료 화면에서 뒤로 가기를 눌러 제출 화면이 다시 눌리는 상태로 열리는지 본다. 개발 도구로 요청을 붙잡은 채 버튼을 두 번 눌러 요청 수를 센다. 로그인·결제처럼 해 보면 부작용이 있는 경우는 코드에서 본다
  - 검사: 「두 번 눌림 방지 없음」(`check-screen.mjs`, 결제·주문·송금 버튼에 누른 뒤 잠그는 코드가 없을 때). 새로 고침·뒤로 가기는 없음
  - 근거: GOV.UK 질문 페이지(한 번만 일어나는 일은 뒤로 가기가 되풀이하지 않는다), GOV.UK 버튼(두 번 보내는 실수), Vercel Web Interface Guidelines, Post/Redirect/Get(간접)
- **사고-6 (꼭) 로그아웃한 뒤 뒤로 가기로 개인 화면이 다시 보이지 않는다.**
  - 브라우저는 뒤로 가기로 돌아온 페이지를 저장해 둔 그대로 보이기도 한다(bfcache). 개인 화면은 `Cache-Control: no-store`를 주고, 돌아온 페이지(`pageshow`의 `persisted`)에서 로그인 상태를 다시 보고, 한 페이지 앱은 로그아웃할 때 메모리에 든 개인 정보를 비운다. 공용 기기에서 다음 사람이 본다
  - 눈으로: 로그인 → 내 정보 → 로그아웃 → 뒤로 가기를 눌러 이름·주소·주문 내역이 보이면 위반이다. 로그인할 수 없으면 코드에서 로그아웃 처리와 캐시 설정을 본다
  - 검사: 없음
  - 근거: web.dev bfcache(돌아온 페이지는 헤더를 다시 보지 않는다), Chrome bfcache와 no-store, OWASP 세션 관리
- **사고-7 (확인) 여럿이 같이 고치는 것은 나중에 저장하는 사람이 앞사람이 고친 것을 모르고 덮지 않게 알리고, 내 글은 남긴 채 고르게 한다.**
  - 공지·문서·재고처럼 두 사람(또는 한 사람의 두 탭)이 같은 것을 동시에 고칠 수 있을 때다. 알리고 고르게 할지, 칸마다 합칠지, 고치는 동안 잠글지는 서비스가 정한다
  - 눈으로: 두 탭에서 같은 것을 열어 한쪽에서 먼저 저장하고, 다른 쪽에서 저장해 본다
  - 검사: 없음
  - 근거: MediaWiki 편집 충돌

## 할 일이 보이나

화면을 열었을 때 지금 상태와 해야 할 일이 바로 보이는 것. 실패 이름은 「할 일이 안 보임」.

- **할 일-1 (권장) 스크롤하지 않은 첫 화면에서 지금 상태가 보인다.**
  - 진행 중인지, 막혔는지, 끝났는지. 상태를 보려고 끝까지 내려가야 하면 안 된다
  - 눈으로: 스크롤하지 않은 첫 화면만 보고 「지금 어떤 상태고 내가 뭘 하면 되나」에 답해 본다
  - 검사: 없음
  - 근거: NN/g 1번 휴리스틱(시스템 상태 보이기), KRDS 신청 패턴 [필수] 현재 진행 상태 제공, Built for Shopify 4.2.3(첫 화면에 잘 돌고 있는지)
- **할 일-2 (권장) 화면 전체를 요약하는 것은 위쪽에 한 번만 둔다.**
  - 결과 수·합계처럼 화면 전체를 요약하는 것은 맨 아래가 아니라 위에. 같은 상태 글(「진행 중 아님」)을 여러 곳에 되풀이하지 않는다
  - 눈으로: 요약 숫자가 어디 있는지, 같은 글이 몇 번 나오는지 센다
  - 검사: 없음
  - 근거: Fluent·Microsoft 글쓰기(가장 중요한 것을 앞에), 토스 라이팅 원칙(화면 속 잡초 제거), Shopify(같은 내용을 한 페이지에 두 번 보이지 않는다)
- **할 일-3 (확인) 상태가 바뀌면 가장 눈에 띄는 버튼도 따라 바뀐다.**
  - 다 끝났으면 마무리 동작을, 막혔으면 막힌 이유를 앞에 둔다. 할 일이 없을 때 강조할 것도 없다
  - 눈으로: 상태를 바꿔 본다(`references/try-pages.md` 「상태 바꿔 보기」). 상태가 바뀌어도 같은 버튼이 늘 같은 세기로 눈에 띄면 짚는다
  - 검사: 없음
  - 근거: 우리 규칙이다. 직접 다룬 출처는 찾지 못했다. 가까운 것은 Built for Shopify 4.2.5(가장 그럴듯한 버튼을 강조), GOV.UK(주 버튼은 하나)
- **할 일-4 (꼭) 검색 결과 화면은 찾은 말을 칸에 남기고, 결과가 없으면 없다고 말하며 조건을 풀 길을 준다.**
  - 빈 목록만 두면 아직 불러오는 중인지, 정말 없는지, 무엇을 바꿔야 하는지 모른다. 어느 조건 때문에 없는지 말하고 그 조건을 빼는 버튼이나 다른 검색어를 함께 둔다. 빈 화면을 어떤 방식으로 그릴지는 패턴 「비어 있을 때」
  - 눈으로: 결과가 없을 말로 찾고 필터도 하나 걸어 본다. 찾은 말이 칸에 남는지, 왜 없는지와 다음에 할 일이 보이는지 본다
  - 검사: 없음
  - 근거: KRDS 검색(검색어 유지, 결과 없음 안내(필수)), NN/g 10가지 휴리스틱(오류를 알아보고 빠져나오기)

## 누른 뒤

누른 다음 무엇이 바뀌었는지 알고, 실패하면 그 자리에서 고칠 수 있는 것. 실패 이름은 「빠진 상태」.

- **누른 뒤-1 (권장) 누른 결과를 누른 자리에서 알린다.**
  - 무엇이 바뀌었는지, 다른 화면으로 옮겨졌으면 왜 거기 왔는지 알린다. 성공 알림은 보조기술도 읽게 한다(`role="status"`, `aria-live`)
  - 예외: 결과가 화면에 그대로 보이는 가벼운 동작(체크 켜기)은 따로 알리지 않아도 된다
  - 눈으로: 눌러 보고 1초 안에 무엇이 달라졌는지 말할 수 있나. 다른 목록으로 넘어갔다면 방금 한 일이 어디 남았나
  - 검사: 없음
  - 근거: NN/g 1번 휴리스틱, Carbon 알림 패턴(작업한 영역에 바로), Primer 저장 패턴(페이지가 그대로면 인라인 메시지), GOV.UK 완료 페이지, WCAG 2.2 4.1.3
- **누른 뒤-2 (꼭) 실패하면 그 자리에 이유와 고칠 방법이 남는다.**
  - 사라지는 토스트로만 알리지 않는다. 무엇이 틀렸는지와 다시 할 방법을 그 칸 옆에 같이 쓴다. 적은 값을 지우지 않는 것은 입력-6
  - 눈으로: 빈 칸·틀린 값으로 제출하고, 무엇이 틀렸는지 그 자리에서 알 수 있는지 본다
  - 검사: 오류를 토스트로만 알림(`check-screen.mjs`)
  - 근거: GOV.UK 오류 메시지(필드 옆, 입력값 보존), Carbon 모달(닫지 않고 인라인), Built for Shopify 4.2.4, NN/g 오류 메시지 글, WCAG 2.2 3.3.1, 3.3.3
- **누른 뒤-3 (권장) 점수·등급 같은 결과에는 뜻과 바뀐 이유를 함께 보인다.**
  - 「62점」「C 등급」만 두면 좋은 건지 나쁜 건지, 무엇을 하면 바뀌는지 모른다. 몇 점 중인지, 어느 구간인지, 지난번보다 왜 오르내렸는지를 같은 자리에 쓴다
  - 눈으로: 점수·등급·배지만 보고 좋은 건지 나쁜 건지, 왜 바뀌었는지 답해 본다
  - 검사: 없음
  - 근거: 앱인토스 블로그(점수에는 뜻과 바뀐 이유를)
- **누른 뒤-4 (꼭) 결제·제출이 실패하면 이유와 다시 할 길을 그 자리에 보이고, 첫 화면으로 보내지 않는다.**
  - 「결제에 실패했어요」 토스트만 띄우거나 첫 화면으로 보내지 않는다. 왜 실패했는지(카드 한도, 재고), 무엇을 하면 되는지를 실패한 자리에 남긴다. 담은 것과 적은 값을 지키는 것은 입력-6
  - 눈으로: 결제·제출이 실패하는 경우(카드 거절, 재고 없음, 연결 끊김)를 만들어 보고, 실패한 자리에 이유와 다시 할 길이 남는지 본다. 실제 결제는 하지 않고, 요청을 막거나(개발 도구 요청 차단) 코드에서 본다
  - 검사: 「오류를 토스트로만 알림」(`check-screen.mjs`). 첫 화면으로 보내는지는 없음

  - 눈으로: 확인 링크를 한 번 쓴 뒤 다시 열고, 시간이 지난 링크도 열어 본다

  - 근거: GOV.UK 이메일 확인, GOV.UK 페이지를 찾을 수 없을 때

  - 눈으로: 개발자 도구로 연결을 끊고(오프라인) 저장·체크를 눌러 본다. 화면이 저장된 척 남는지, 실패를 알리는지 본다

  - 눈으로: 저장한 뒤 새로 고침하고, 그 주소를 새 탭에 열어 본다
  - 검사: 없음
  - 근거: 우리 규칙이다. 직접 다룬 출처는 찾지 못했다. 가까운 것은 MDN replaceState(기록을 쌓지 않고 주소 바꾸기)

  - 검사: 없음
  - 근거: web.dev 오프라인 UX

## 입력

칸마다 무엇을 쓰는지 알고, 쓰는 동안 막히지 않고, 틀려도 그 자리에서 고칠 수 있는 것. 실패 이름은 「헷갈림」.

- **입력-1 (권장) 입력 칸마다 보이는 레이블을 두고, placeholder로 대신하지 않는다.**
  - placeholder는 쓰기 시작하면 사라져서, 다 쓴 뒤 무엇을 쓰던 칸인지 확인할 수 없다. 옅은 글씨라 잘 안 보이고, 이미 쓴 값처럼 보여 빈 칸을 지나치기도 한다. 예시(「예: 010-1234-5678」)는 레이블 아래 도움말로 둔다
  - 눈으로: 칸에 글을 쓴 뒤에도 무엇을 쓰는 칸인지 보이나. 쓴 칸들을 훑어 맞게 썼는지 확인할 수 있나
  - 검사: 「placeholder만 있는 입력」(`check-screen.mjs`)
  - 근거: KRDS 기본 패턴(입력폼·개인 식별 정보 입력)(플레이스홀더를 레이블 대신 쓰지 않는다), W3C WAI 폼 튜토리얼(Form Instructions)(placeholder는 레이블을 대신하지 못한다. 화면 읽기 프로그램이 레이블로 다루지 않고, 쓰기 시작하면 사라진다. WCAG 3.3.2 자체는 placeholder만 있는 칸을 실패로 정하지 않아 「권장」으로 둔다(2026-11-12 확인)), Primer 디자이너 체크리스트(폼), Vercel Web Interface Guidelines(Forms)
- **입력-2 (권장) 칸마다 맞는 자판이 뜨고, 브라우저가 이름·연락처를 채울 수 있게 한다.**
  - 전화번호는 `type="tel"`, 이메일은 `type="email"`, 숫자만 쓰는 칸은 `inputmode="numeric"`이라야 휴대폰이 맞는 자판을 연다. 이름·전화번호·주소에는 `autocomplete`(name, tel, email, postal-code 등)를 달아 브라우저가 채우게 하고, 이미 받은 정보를 다시 쓰게 하지 않는다

  - 검사: 없음
  - 근거: WCAG 2.2 1.3.5, KRDS 기본 패턴(개인 식별 정보 입력)(autocomplete), Vercel Web Interface Guidelines(Forms)
- **입력-3 (꼭) 붙여넣기를 막지 않는다.**

- **입력-4 (권장) 입력이 다 맞을 때까지 제출 버튼을 꺼 두지 않는다.**

  - 검사: 없음
  - 근거: GOV.UK 답 확인, KRDS 신청(신청 내용 확인(필수))

## 길과 뒤로 가기

지금 어디 있는지 알고, 가려는 곳으로 가고, 어느 화면에서든 나올 수 있는 것. 실패 이름은 「헷갈림」.

- **길-1 (권장) 다른 화면으로 가는 것은 버튼이 아니라 링크로 만든다.**
  - `<a href>`라야 새 탭으로 열기, 주소 복사, 뒤로 가기, 화면 읽기 프로그램의 링크 목록이 된다. 버튼에 누르면 주소를 바꾸는 코드를 달면 이것이 모두 안 된다. 반대로 화면 안에서 무엇을 하는 것(저장, 열고 닫기)은 버튼이다
  - 눈으로: 목록의 항목·메뉴를 오른쪽 단추로 눌러 「새 탭에서 열기」가 나오나. 열고 나서 뒤로 가기로 돌아오나
  - 검사: 「링크가 아닌 이동」(`check-screen.mjs`)
  - 근거: Vercel Web Interface Guidelines(이동은 링크로)
- **길-2 (권장) 메뉴와 탭에서 지금 있는 곳을 표시한다.**
  - 눈에는 굵기·밑줄·바탕처럼 색 말고도 보이는 표시로, 화면 읽기 프로그램에는 `aria-current="page"`로 알린다
  - 눈으로: 메뉴만 보고 지금 어느 화면인지 말할 수 있나. 색을 빼고 봐도 알 수 있나
  - 검사: 없음
  - 근거: 우리 규칙이다. 가까운 것은 NN/g 1번 휴리스틱(시스템 상태 보이기), W3C COGA(필요한 것을 찾게)
- **길-3 (권장) 화면마다 무슨 화면인지 알 수 있는 페이지 제목을 단다.**
  - 브라우저 탭, 방문 기록, 북마크, 화면 읽기 프로그램이 처음 읽는 것이 페이지 제목(`<title>`)이다. 모든 화면이 서비스 이름뿐이면 탭 여럿을 구분하지 못한다. 「지금 화면 – 서비스 이름」 순서로 쓴다
  - 눈으로: 화면 두세 개를 탭으로 열어 탭 제목만으로 구분되나
  - 검사: 없음
  - 근거: WCAG 2.2 2.4.2
- **길-4 (꼭) 막다른 화면 없이 어디서든 나갈 길을 둔다.**
  - 완료·결과 화면, 전체 화면 안내, 오류 화면에도 닫기·뒤로·처음으로 중 하나는 보인다. 다음에 할 일이 있으면 그것을 앞에 둔다
  - 눈으로: 끝까지 해 본 뒤 마지막 화면에서 나갈 버튼이 있나. 휴대폰 뒤로 가기 말고도 화면 안에 길이 있나
  - 검사: 없음
  - 근거: 앱인토스 소비자 UX 가이드(다크패턴 방지: 나갈 선택지 없음), NN/g 10가지 휴리스틱(사용자 통제와 자유)
- **길-5 (꼭) 끝낸 흐름(로그인·본인 확인·결제·신청)은 뒤로 가기로 다시 열리지 않는다.**
  - 끝낸 단계로 돌아오면 같은 양식을 다시 보이지 않고 「이미 끝났다」는 안내나 다음 화면으로 보낸다. 끝낸 화면은 기록을 replace로 바꿔 두면 뒤로 가기가 그 앞 화면으로 간다. 로그인 화면을 기록에 남기지 않는 것도 같다
  - 예외: 모달로 띄운 로그인
  - 눈으로: 신청·결제를 끝낸 뒤 뒤로 가기를 눌러 제출 화면이 다시 눌리는 상태로 열리나 본다. 로그인한 뒤 뒤로 가기를 눌러 로그인 화면이 다시 나오나 본다. 로그인·결제처럼 해 보면 부작용이 있는 경우는 코드에서 본다
  - 검사: 없음
  - 근거: GOV.UK 질문 페이지, DfE 디자인 기록(끝난 뒤 뒤로 가기), Baymard 뒤로 가기 기대. 로그인에 그대로 적은 1차 출처는 없다(로그인은 우리 판단)
- **길-6 (권장) 로그인을 마치면 하려던 곳으로 돌아간다.**
  - 로그인을 요구한 화면 주소를 로그인 주소에 실어(`?next=/meet/12`) 마친 뒤 그리로 보낸다. 돌아갈 주소는 같은 사이트 경로만 받는다(열린 리다이렉트 막기). 초대·한 번 쓰는 링크처럼 다시 찾을 길이 없으면 꼭이다
  - 눈으로: 로그아웃 상태로 로그인이 필요한 주소를 열어 로그인 주소에 `returnTo`·`next`·`redirect`가 실리는지 본다. 로그인할 수 없으면 코드에서 로그인 뒤 이동을 본다
  - 검사: 없음
  - 근거: KRDS 로그인 완료, Baymard 로그인 흐름(34%가 가려던 곳으로 보내지 않는다), OWASP 리다이렉트
- **길-7 (권장) 검색어·필터·정렬·페이지·탭을 주소에 담아, 새로 고침·공유·뒤로 가기 뒤에도 같게 한다.**
  - 화면 상태로만 두면 새로 고침하거나 상세에서 돌아올 때 처음 값으로 돌아간다. KRDS 검색 패턴은 조건 유지를 필수로 둔다. 조건을 바꿀 때마다 기록을 쌓을지는 갈린다(Baymard는 쌓으라고, Smashing은 작은 변화는 쌓지 말라고 한다). 서비스 안에서 하나로 정하고, 입력하는 동안 바뀌는 자동 검색은 replace로
  - 눈으로: 필터를 고르고 새로 고침한다. 상세에 들어갔다 뒤로 온다. 주소를 복사해 새 탭에 연다. 셋 다 같은 조건이 남아야 한다
  - 검사: 없음
  - 근거: Vercel Web Interface Guidelines(주소에 상태), KRDS 검색(조건 유지(필수)), Baymard 뒤로 가기 기대, Smashing 뒤로 가기 UX
- **길-8 (권장) 상세에서 돌아오면 같은 조건과 누른 항목 근처 자리로 돌아간다.**
  - 「더 보기」나 무한 스크롤로 불러온 만큼도 지킨다. 맨 위로 보내거나 처음 몇 개만 다시 보이면 찾던 자리를 다시 찾아야 한다
  - 눈으로: 목록을 내리고 「더 보기」를 한두 번 누른 뒤 아래쪽 항목에 들어갔다 뒤로 온다. 같은 자리, 같은 개수로 돌아와야 한다
  - 검사: 없음
  - 근거: Baymard 같은 자리로 돌아오기(13%가 맨 위로 보낸다), NN/g 무한 스크롤, MDN scrollRestoration, Chrome 스크롤 복원
- **길-9 (권장) 페이지처럼 보이는 시트·창이 열려 있으면 뒤로 가기는 그것만 닫는다.**
  - 열 때 기록을 한 칸 쌓고, ✕로 닫으면 그 칸도 걷어 다음 뒤로 가기가 한 번에 앞 페이지로 가게 한다. 창이 겹쳤으면 뒤로 가기 한 번에 맨 위 하나만 닫는다. 화면 상태로만 열면 뒤로 가기가 아래 페이지까지 떠나 버린다
  - 예외: 작은 팝오버·툴팁·드롭다운은 기록을 쌓지 않는다
  - 눈으로: 휴대폰 폭에서 바텀 시트·전체 화면 창을 열고 뒤로 가기(안드로이드 뒤로, 브라우저 뒤로)를 누른다. 창만 닫히고 아래 페이지는 남아야 한다. ✕로 닫은 뒤 뒤로 가기가 한 번에 앞 페이지로 가는지도 본다
  - 검사: 없음
  - 근거: NN/g 실수로 닫히는 오버레이, Baymard 뒤로 가기 기대(37%가 틀렸다), Apple HIG 모달, MDN CloseWatcher. ✕로 닫을 때 쌓은 기록도 걷는 것은 우리 판단이다
- **길-10 (권장) 링크·알림으로 상세에 바로 들어와도 화면 안의 「뒤로」는 서비스 안(목록·홈)으로 간다.**
  - 앞 기록이 서비스 안이면 기록을 되돌리고, 없으면(검색·공유 링크·알림으로 바로 들어왔으면) 위 단계 화면으로 보낸다. `history.back()`만 쓰면 빈 화면이나 다른 사이트로 나간다. 알림을 누르면 그 항목에 바로 닿고, 로그인이 필요하면 로그인 뒤 그 항목으로 간다(길-6)
  - 눈으로: 상세 주소를 새 탭에 바로 열고 화면 안 「뒤로」를 눌러 본다. 서비스 목록이나 홈으로 가야 한다
  - 검사: 없음
  - 근거: Android 내비게이션 원칙(딥 링크도 가상 기록), 당근 Stackflow history-sync. 웹에 그대로 적은 1차 출처는 없다
- **길-11 (권장) 여러 단계 폼은 단계마다 기록을 한 칸씩 쌓아, 브라우저 뒤로 가기와 화면의 「이전」이 같은 곳으로 간다.**
  - 단계를 화면 상태로만 바꾸면 브라우저 뒤로 가기가 폼 전체를 떠나 앞 페이지로 간다. 휴대폰에서는 화면 버튼보다 뒤로 가기 동작을 더 자주 쓴다. 단계를 나누는 방식은 패턴 「여러 단계 흐름」
  - 눈으로: 두세 단계 들어간 뒤 브라우저 뒤로 가기를 눌러 한 단계 앞으로 가는지 본다
  - 검사: 없음
  - 근거: Baymard 뒤로 가기 기대, Android 내비게이션 원칙, GOV.UK 뒤로 링크, NN/g 사용자 통제
- **길-12 (권장) 한 탭에서 로그아웃하면 다른 탭도 늦어도 다음 동작 때 알고, 그 탭에 쓰던 것은 다시 로그인한 뒤 이어 쓴다.**
  - 다른 탭이 로그인된 척 남아 있다가 누르는 순간 로그인 화면으로 넘어가면 쓰던 글을 잃는다. 탭끼리 알리는 방법(BroadcastChannel)으로 바로 알리거나, 적어도 다음 요청 때 알린다
  - 눈으로: 두 탭을 열고 한 탭에서 로그아웃한 뒤, 다른 탭에서 쓰던 것을 보내 본다
  - 검사: 없음
  - 근거: MDN BroadcastChannel, OWASP 세션 관리

## 누구나

마우스 없이, 화면을 키워서, 움직임과 소리 없이, 색을 못 가려도 쓸 수 있는 것. 실패 이름은 「읽기·누르기 어려움」.

- **누구나-1 (꼭) 모든 기능을 키보드로 쓸 수 있고, 초점이 갇히지 않는다.**
  - 눈으로: Tab만으로 주요 동작을 끝까지 해 본다. 들어간 곳에서 Tab·Shift+Tab·Esc로 빠져나올 수 있나
  - 검사: 「키보드로 못 누르는 곳」(`check-screen.mjs`, onclick·@click만 단 div·span·li·img. 스크립트에서 붙인 클릭은 못 본다), 이름 없는 버튼. 흐름 전체는 없음
  - 근거: WCAG 2.2 2.1.1, 2.1.2
- **누구나-2 (권장) 대화상자는 안에서 초점이 돌고, 닫으면 연 자리로 돌아간다.**
  - 연 버튼이 사라졌으면(지운 행) 흐름상 다음 자리(이웃 행)로 보낸다. 페이지 맨 위로 떨어지게 두지 않는다
  - 눈으로: 창을 열고 Tab을 여러 번 눌러 창 밖으로 나가지 않는지, 닫은 뒤 초점이 어디 있는지 본다
  - 검사: 없음
  - 근거: WAI-ARIA APG 모달 대화상자, Primer 초점 관리, Fluent Dialog, Carbon 대화상자 패턴
- **누구나-3 (권장) 꼭 필요한 정보를 마우스를 올려야 보이는 설명(툴팁)에만 두지 않는다.**
  - 키보드·터치로는 볼 수 없다. 꺼진 버튼의 이유, 위험 안내는 화면에 글로 둔다
  - 눈으로: `title`이 달린 꺼진 버튼, 아이콘에만 붙은 설명을 찾는다
  - 검사: 「꺼진 이유가 title에만 있음」(`check-screen.mjs`, 꺼진 버튼이나 감싼 span의 title. 툴팁 라이브러리는 못 본다)
  - 근거: WCAG 2.2 1.4.13, NN/g 툴팁 글(과업에 필요한 정보는 화면에), Primer 툴팁, Primer 디자이너 체크리스트, Carbon 비활성 상태(막혔으면 풀 방법을 인라인으로)
- **누구나-4 (확인) Esc로 닫히는지와 확인 창 버튼 순서를 서비스 안에서 하나로 맞춘다.**
  - 갈리는 기준이다. Primer·Carbon은 Esc로 닫히고 Fluent의 경고 창은 닫히지 않는다. 버튼 순서는 Carbon·Apple이 「취소 왼쪽, 확정 오른쪽」, GOV.UK는 주 동작이 먼저다
  - 눈으로: 확인 창 두세 개를 열어 순서와 Esc 동작이 같은지 본다
  - 검사: 없음
- **누구나-5 (꼭) 화면 확대를 막지 않는다.**
  - viewport에 `user-scalable=no`나 `maximum-scale=1`을 넣지 않는다. 글자를 200%로 키워도 잘리거나 겹치지 않고 줄이 바뀌게 만든다
  - 눈으로: 휴대폰에서 두 손가락으로 벌려 키워 본다. 기기 글자 크기를 가장 크게 하고 다시 본다
  - 검사: 「확대 막기」(`check-screen.mjs`, viewport의 user-scalable=no·maximum-scale=1)
  - 근거: WCAG 2.2 1.4.4, KRDS 디지털 포용, 당근 SEED 포용 디자인(시스템 글자 크기를 따른다)
- **누구나-6 (권장) 기기의 「움직임 줄이기」 설정을 따르고, 오래 움직이는 것은 멈추거나 건너뛰게 한다.**
  - 기기에서 움직임 줄이기를 켠 사람에게는 등장·반복 움직임을 끈다(`prefers-reduced-motion`). 저절로 넘어가는 배너처럼 계속 움직이는 것에는 멈춤을, 2초 넘는 움직임에는 건너뛰기를 둔다
  - 눈으로: 기기의 움직임 줄이기를 켜고 다시 본다. 저절로 넘어가는 것을 멈출 수 있나
  - 검사: 「저절로 움직이는데 멈춤 없음」(`check-screen.mjs`), 움직임 줄이기 설정을 따르는 CSS가 없음(`check-visual.mjs`). 2초 넘는 한 번짜리 움직임은 없음
  - 근거: 당근 SEED 포용 디자인(애니메이션 끄기, 2초 넘으면 건너뛰기), WCAG 2.2 2.3.3, WCAG 2.2 2.2.2
- **누구나-7 (꼭) 소리 나는 것을 저절로 틀지 않는다.**
  - 영상·소리는 사용자가 눌러서 튼다. 저절로 틀어야 하면 소리를 끈 채로(`muted`) 틀고 멈춤을 둔다. 저절로 나는 소리는 화면 읽기 프로그램의 말소리를 덮고, 조용한 곳에서 쓰는 사람을 놀라게 한다
  - 눈으로: 화면을 열자마자 소리가 나는 것이 있나. 있으면 바로 끌 수 있나
  - 검사: 「소리 나는 자동 재생」(`check-screen.mjs`)
  - 근거: WCAG 2.2 1.4.2, KWCAG 2.2(자동 재생 금지), 당근 SEED 포용 디자인(자동 재생은 기본으로 끈다)
- **누구나-8 (꼭) 시간 제한은 끝나기 전에 알리고 늘릴 수 있게 한다.**
  - 로그인 유지, 좌석·재고 잡아 두기처럼 시간이 정해진 것은 남은 시간을 보이고, 끝나기 전에 늘릴지 묻는다(KRDS 로그인 패턴은 만료 20초 전). 시간이 끝나 로그아웃됐어도 다시 로그인하면 고른 것과 쓴 것을 이어 쓰게 한다
  - 예외: 실시간 경매·시험처럼 시간이 일의 일부인 것. 이때는 남은 시간을 처음부터 보인다
  - 눈으로: 시간 제한이 있는 화면에서 끝나기 전에 알림이 오는지, 늘릴 수 있는지 기다려 본다
  - 검사: 시간이 지나면 저절로 바뀌는데 끄거나 늘릴 방법이 없음(`check-visual.mjs`, 「30초 동안」「사라져요」처럼 화면에 적힌 글로만 본다)
  - 근거: KRDS 서비스 패턴(로그인)(만료 20초 전에 연장·로그아웃), WCAG 2.2 2.2.1, DWP 세션 만료(끝나기 2분 전에 알림), WCAG 2.2 2.2.5(다시 인증해도 잃지 않기)
- **누구나-9 (꼭) 뜻을 색만으로 전하지 않는다.**
  - 상태 점에는 글자를, 오류 칸에는 빨간 테두리와 함께 고칠 말을, 그래프에는 색과 함께 이름표를 둔다. 색을 못 가리는 사람, 흑백 인쇄, 햇빛 아래 화면에서도 뜻이 남게
  - 눈으로: 화면을 흑백으로 바꿔 보고(브라우저 개발 도구의 색각 흉내) 상태와 오류를 그대로 읽을 수 있나
  - 검사: 「상태를 색만으로 표시」(`check-screen.mjs`, 글자·aria-label이 없는 status·badge·dot 표시)
  - 근거: WCAG 2.2 1.4.1, Primer 디자이너 체크리스트(색)

## 끼어들지 않기

하려던 일을 창·광고·알림이 가로막지 않는 것. 실패 이름은 「방해」.

- **방해-1 (권장) 들어오자마자 창·광고·알림 동의를 띄우지 않는다.**
  - 먼저 하려던 화면을 보인다. 알림 허용·앱 설치·이벤트는 그것이 쓸모 있는 순간에 그 자리에서 묻는다(알림은 상품을 담은 뒤, 예약을 마친 뒤)
  - 눈으로: 처음 들어왔을 때 본 화면보다 먼저 뜨는 것이 있나
  - 검사: 「처음부터 열린 창」(`check-screen.mjs`)
  - 근거: 앱인토스 소비자 UX 가이드(다크패턴 방지: 들어오자마자 광고·알림 시트), Built for Shopify 4.3.3·4.3.4
- **방해-2 (권장) 이미 거절한 것을 다시 묻지 않는다.**
  - 닫은 창을 다음 화면에서 또 띄우지 않는다. 다시 물어야 하면 「7일간 보지 않기」처럼 언제 다시 묻는지 고르게 하고 그 기간을 지킨다
  - 눈으로: 띄운 창을 닫고 화면을 몇 번 옮겨 다니며 같은 창이 또 뜨는지 센다
  - 검사: 없음
  - 근거: 공정위 전자상거래법 개정 다크패턴 6유형(반복간섭, 2025-02-14 시행, 간접), 공정위 다크패턴 운영 가이드라인(2026-10-06, 13유형, 간접), deceptive.design(Nagging)
- **방해-3 (꼭) 뒤로 가기를 붙잡거나 가로채지 않는다.**
  - 뒤로 가기는 앞 화면으로 간다. 「지금 나가면 쿠폰이 사라져요」처럼 나가려는 사람을 붙잡는 창을 끼우거나, 혜택·알림 동의·광고 화면이나 가 본 적 없는 페이지를 기록에 끼워 넣지 않는다. 광고·라이브러리가 넣은 것이어도 그 서비스 책임이다(Google 검색은 2026-06-15부터 이것을 스팸으로 본다). 쓰는 사람을 속여 붙잡는 일이라 「속이지 않기」와도 닿는다
  - 예외: 쓰던 글·입력이 사라질 때 저장하지 않고 나갈지 묻는 것
  - 눈으로: 여러 화면을 들어간 뒤 뒤로 가기를 눌러 한 번에 앞 화면으로 가는지 본다. 처음 들어온 페이지에서 뒤로 가기를 눌러 들어오기 전 사이트로 나가는지 본다
  - 검사: 없음
  - 근거: 앱인토스 소비자 UX 가이드(다크패턴 방지: 뒤로 가기를 막는 시트), Google 검색 「뒤로 가기 가로채기」 스팸 정책(2026-04-13 발표), NN/g 사용자 통제와 자유
- **방해-4 (권장) 알림·배너를 한 화면에 쌓지 않는다.**
  - 띠 배너·토스트·창이 여럿 겹치면 정작 처리할 알림을 놓친다. 급한 정도로 자리를 나누고(지금 고쳐야 하는 것은 그 자리에, 소식은 알림함에) 한 번에 하나만 앞에 둔다
  - 눈으로: 처음 열었을 때 보이는 알림·배너·토스트를 센다. 그중 지금 해야 하는 것이 가장 앞에 있나
  - 검사: 없음
  - 근거: KRDS 기본 패턴(모바일 알림)(급한 정도로 채널을 나눈다), Built for Shopify 4.3.3·4.3.4
- **방해-5 (권장) 로그인은 꼭 필요한 순간에 묻고, 로그인하면 무엇이 좋은지 말하며 「로그인 안 함」을 둔다.**
  - 들어오자마자 로그인부터 요구하면 무엇을 하는 서비스인지 보기도 전에 떠난다. 둘러보기는 로그인 없이 되게 하고, 저장·결제처럼 계정이 필요한 순간에 묻는다. 로그인 바로 뒤에 알림 동의를 잇지 않는다
  - 눈으로: 로그아웃 상태로 처음 들어가 무엇까지 로그인 없이 볼 수 있는지, 언제 왜 로그인을 묻는지 본다
  - 검사: 없음
  - 근거: KRDS 로그인(「로그인 안 함」), 앱인토스 로그인·알림 시점 글(들어오자마자 로그인을 요청하면 완료율 49.6%, 2026-10-15)

## 속이지 않기

고른 적 없는 것이 골라지지 않고, 낼 돈과 그만두는 길이 숨지 않는 것. 실패 이름은 「속임」.

- **속임-1 (꼭) 동의와 추가 상품을 미리 골라 두지 않는다.**
  - 마케팅 수신 동의, 보장·보험 같은 추가 상품, 정기 결제 전환은 비운 채로 시작한다. 사용자가 고른 것만 넣는다. 필수와 선택은 글로 나눈다(입력-5)
  - 눈으로: 결제·가입 화면에서 처음부터 켜진 체크와 골라진 선택지를 찾고, 그것이 돈이나 동의와 이어지는지 본다
  - 검사: 「미리 체크된 동의」(`check-screen.mjs`)
  - 근거: 공정위 전자상거래법 개정 다크패턴 6유형(사전선택: 돈 드는 추가 상품을 미리 고름, 2025-02-14 시행, 간접), 공정위 다크패턴 운영 가이드라인(2026-10-06, 13유형, 간접), KRDS 기본 패턴(동의)([필수]·[선택], 동의 안 함), deceptive.design(Preselection). 돈 드는 추가 상품은 전자상거래법이, 마케팅 수신 동의는 KRDS 동의 패턴과 deceptive.design이 근거다
- **속임-2 (권장) 거절 쪽을 흐리게 만들어 한쪽으로 몰지 않는다.**
  - 받기와 거절은 둘 다 누를 것으로 보이게 둔다. 거절을 옅고 작은 글씨나 멀리 떨어진 링크로 숨기면 못 찾거나 잘못 누른다(잘못된 계층구조)
  - 예외: 주 동작과 닫기처럼 무게가 다른 선택지는 다르게 강조해도 된다. 문제는 사용자에게 손해인 쪽만 키우고 다른 쪽을 숨길 때다
  - 눈으로: 돈이 드는 쪽과 거절 쪽 버튼을 견준다. 거절 쪽 글자가 옅거나 작아 찾기 어렵나
  - 검사: 없음
  - 근거: 공정위 전자상거래법 개정 다크패턴 6유형(잘못된 계층구조, 2025-02-14 시행, 간접), 공정위 다크패턴 운영 가이드라인(2026-10-06, 13유형, 간접), deceptive.design(Visual interference)
- **속임-3 (권장) 거절하는 말로 죄책감을 주지 않는다.**
  - 「아니요, 할인은 필요 없어요」「혜택을 포기할게요」처럼 거절하는 사람을 깎는 말을 버튼에 쓰지 않는다. 「받지 않기」「닫기」처럼 하는 일만 말한다(글-1)
  - 눈으로: 거절·닫기 버튼 글만 소리 내어 읽어 본다. 누르는 사람을 탓하는 말인가
  - 검사: 없음
  - 근거: deceptive.design(Confirmshaming)
- **속임-4 (꼭) 처음 보인 가격이 낼 가격이다.**
  - 청소비·수수료·필수 옵션을 결제 마지막에 더하지 않는다. 목록과 상세에서 낼 돈 전체를 보이고, 나눈 내역은 그 옆에 둔다(순차공개 가격). 배송비처럼 조건에 따라 바뀌면 처음부터 같은 자리에 쓴다
  - 눈으로: 목록에서 본 가격과 결제 직전 금액을 견준다. 늘었다면 늘어난 것이 처음부터 보였나
  - 검사: 없음
  - 근거: 공정위 전자상거래법 개정 다크패턴 6유형(순차공개 가격, 2025-02-14 시행, 간접), 공정위 다크패턴 운영 가이드라인(2026-10-06, 13유형, 간접), deceptive.design(Hidden costs), FTC 「Bringing Dark Patterns to Light」
- **속임-5 (꼭) 해지·탈퇴를 가입보다 어렵게 만들지 않는다.**
  - 가입을 한 화면에서 했으면 해지도 그만큼이다. 메뉴 깊이 숨기거나, 전화·상담으로만 받거나, 붙잡는 화면을 여러 번 끼우지 않는다. 해지 뒤에 무엇이 언제 끝나는지 알린다
  - 눈으로: 가입할 때와 해지할 때 누르는 횟수와 화면 수를 센다
  - 검사: 없음
  - 근거: 공정위 전자상거래법 개정 다크패턴 6유형(취소·탈퇴 방해, 2025-02-14 시행, 간접), 공정위 다크패턴 운영 가이드라인(2026-10-06, 13유형, 간접), deceptive.design(Hard to cancel), FTC 「Bringing Dark Patterns to Light」
- **속임-6 (꼭) 권한은 쓰는 순간에 이유와 함께 묻고, 거부해도 나머지는 쓸 수 있게 한다.**
  - 위치·사진·알림 권한을 앱을 열자마자 한꺼번에 묻지 않는다. 그 기능을 누른 순간에 왜 필요한지 먼저 말하고 묻는다. 거부하면 그 기능만 다른 길(직접 고르기)로 두고 나머지는 그대로 쓰게 한다
  - 눈으로: 권한 창에서 모두 「허용 안 함」을 고른 뒤 앱을 어디까지 쓸 수 있는지 본다
  - 검사: 없음
  - 근거: 앱인토스 출시 체크리스트(권한을 거부해도 나머지 기능이 돌아가야 한다), KRDS 기본 패턴(동의)

## 화면 글

버튼과 안내 글이 하는 일을 정확히, 한 목소리로 말하는 것. 실패 이름은 「헷갈림」.

- **글-1 (권장) 버튼 이름은 하는 일을 말한다.**
  - 「확인」「예」「완료」 대신 「삭제」「종료」「보내기」. 확인 창 제목의 동사와 버튼 이름을 맞춘다. 닫기만 하는 쪽은 「취소」보다 「닫기」가 오해가 적을 때가 있다(「QA 취소」로 읽히는 경우)
  - 예외: 알리기만 하는 창의 「확인」
  - 눈으로: 버튼 글만 읽고 누른 뒤 무슨 일이 나는지 답할 수 있나
  - 검사: 버튼이 둘인데 「확인·예」인 대화상자(`check-screen.mjs`)
  - 근거: 조사한 모든 곳이 같은 말을 한다. Apple, Carbon, Shopify, Primer, Atlassian, Fluent, GOV.UK, KRDS, 토스, 앱인토스 소비자 UX 가이드(「닫기」)
- **글-2 (확인) 한 화면 안에서 말투가 섞이지 않는다.**
  - 「~해요」「~합니다」「~다」가 한 화면에 섞이면 여러 사람이 만든 화면처럼 읽힌다. 상황에 따라 바뀌어도 되는 것은 어조(오류는 더 짧고 직접)이고, 말투는 하나로 둔다
  - 예외: 사용자에게 하는 말(안내·상태·오류)과 사전식 설명(컴포넌트 정의, 목록의 짧은 설명)을 다른 말투로 정해 둔 서비스. 그 경우는 갈래마다 하나로 맞는지를 본다(이 카탈로그 사이트가 그렇다. 2026-11-11)
  - 눈으로: 안내 글·빈 화면·오류·확인 창 글의 끝맺음을 모아 본다
  - 검사: 「말투가 섞임」(`check-screen.mjs`, 끝맺음이 있는 문장에서 해요체·합니다체·한다체 중 두 가지 이상이 각각 2문장 이상 나오면. 자주 묻는 질문(summary·dt)과 버튼·라벨 글은 세지 않는다. 서비스가 직접 묻는 확인 창 질문(「~할까요?」)은 그 서비스의 말이라 센다. `--rules`·`--house`에서는 「정한 건지 확인」으로 간다)
  - 근거: Shopify 콘텐츠(목소리는 같게, 어조는 상황에 맞게), 토스(해요체 필수), NN/g 일관성 글. 글투는 서비스가 정하는 것이라 「확인」이다
- **글-3 (권장) 숫자·금액·날짜 형식을 한 화면에서 하나로 쓴다.**
  - 「12,000원」「₩8500」「1.5만 원」, 「2026-11-02」「11/5」「11월 9일」이 섞이면 견주기 어렵다. 사용자 지역에 맞는 형식(`Intl.NumberFormat`, `Intl.DateTimeFormat`)으로 한 곳에서 만들어 쓴다
  - 눈으로: 금액·날짜·수가 나오는 곳을 모아 쓰는 형식이 몇 가지인지 센다
  - 검사: 없음
  - 근거: Vercel Web Interface Guidelines(Locale-aware formats)

## 리뷰에 쓰는 법

- 걸린 규칙은 「무엇이 / 왜(규칙 이름과 근거) / 어떻게」 한 줄로, 실패 이름 아래에 둔다
- 「검사: 없음」인 규칙은 눌러 보고 확인한 것만 쓴다. 못 해 본 것(로그인 뒤, 지우기처럼 남에게 영향이 가는 동작)은 「확인 못 한 것」에 적고 위반이라고 하지 않는다
- 「먼저 고칠 셋」은 값 검사와 이 문서를 같이 놓고 고른다. 「꼭」이 걸렸으면 대개 그것이 먼저다
- 화면을 만드는 쪽이면: 「꼭」은 모두 지키고, 「권장」은 계획에 어떻게 할지 한 줄씩 적는다
